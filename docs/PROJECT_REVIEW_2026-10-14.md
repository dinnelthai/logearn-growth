# 项目深度复盘：功能、口径与缺陷

审计日期：2026-10-14，Asia/Bangkok。对象为当前工作区（含尚未提交的 CRM、用户标签和导航改动），不是已发布版本保证。以下保留原始审计证据；用户随后要求修复，F1–F8 的完成情况见文末。

## 结论

四入口、CRM 与活动共用工作台、用户标签供分析复用，整体方向合理。账号所有权、交易用户身份、配置保存和标签规模控制还没有贯穿整个项目，已有功能组合使用会暴露缺陷。

确认 8 项需要修复的问题，其中 2 项 P1、6 项 P2。未来事件问题属于可复现的输入防御缺陷，当前实库没有观测到这类数据。另有 5 项设计问题需要明确取舍。

## 验证范围

- 后端全量测试：79 / 79 通过。
- 前端全量测试：39 个测试文件，162 / 162 通过。
- 共 241 项现有测试通过；不覆盖本报告全部跨模块与异常输入场景。
- 使用内存 SQLite、独立 Express 应用、模拟失败响应和模拟 PG 驱动做反例，不改变正式群组或业务数据。
- 对远程业务库仅执行只读聚合：交易身份映射、未来 / 负时间事件。
- 未执行生产端产品埋点验收、部署、多操作者真实浏览器协作或百万用户负载验证。

## F1 · P1 · 旧用户群组没有管理账号隔离，所有权写入也不正确

位置：backend/src/routes/cohorts.js:11、30、54、62、70；backend/src/analytics/loadUsers.js:16；backend/src/index.js:63。

**触发**：管理账号 A 新建群组，管理账号 B 使用同一 API 查询 / 修改该群组。

**实测**：在独立内存服务中，A 创建的群组 `created_by=null`；B 列表返回 1 个 A 的群组，B 获取详情返回 200，B 修改名称返回 200。群组查询和成员解析只按 id，没有 owner 条件。创建接口从客户端 body.created_by 写属主，前端正常创建并不发送这个字段，恶意请求还可以伪造。

**额外后果**：新标签人群接口的 cohort_id 路径要求 created_by 等于当前账号，因此正常新建群组无法通过该检查。当前群组页面将名单转换成 audience_ids，所以不是所有页面操作都立即报错；cohort_id API 路径仍有明确冲突。

**修复**：所有创建使用 req.user.user_id；列表、详情、修改、成员增删、删除与 resolveAudienceUserIds 统一校验 owner。明确旧 null 属主数据的迁移政策，不能自动认领为当前用户。旧群组共享若是产品目标，应设计明确团队权限，不能用缺少过滤实现隐式共享。

## F2 · P1 · 用户分群的交易事实没有使用统一身份映射

位置：backend/src/data/userFacts.js:19、55；backend/src/data/pointsFacts.js:4；backend/src/data/kolMetrics.js:28。

**触发**：旧 user_account 的交易用户 ID 经验证钱包映射到不同的 account_v2 ID。

**代码差异**：CRM 交易、积分与 Credits 使用唯一已验证钱包映射；分群 trade_facts 直接将 trading_transaction.user_id 与 account_v2.account_id 数值关联。

**只读实库证据**：全历史 483 个交易源用户 ID 中，8 个映射到不同的新账号，11 个无法按当前验证规则映射。其中 8 个源 ID 没有同号新账号，直接数字关联会遗漏它们的历史交易贡献；另有 1 个未确认身份存在同号新账号，当前直接关联会在没有验证证据时纳入。

最近 28 天的 34 个交易源 ID，本次核验没有改号或未映射；不能据此说所有近期交易额都已算错。主要确认风险在历史交易记录、交易经历筛选、价值用户池，以及复用这些画像的推荐质量。

**修复**：建立统一只读交易身份事实层，供 CRM、分群、推荐复用。统一身份后再定义记录 / 订单 / 成交去重单位，未匹配或冲突保持质量诊断。平台成交额可保持全平台事实统计，但人数及用户贡献必须采用同一身份口径。

## F3 · P2 · 配置校验仍停留在旧演示选项，合法页面配置无法保存

位置：frontend/src/analytics/configStorage.js:5–8；frontend/src/dashboard.js:123。

**触发 / 复现**：同一个合法基准配置返回 true；选择真实来源 x 返回 false，渠道最近30天返回 false，漏斗最近1天返回 false，路径最近3天返回 false。

页面已经提供这些选项，校验仍只接受旧中文来源和大多数页面7 / 14天。用户点击「保存配置」收到「配置无效」，刷新后的恢复也会拒绝曾保存的真实来源。

**修复**：配置 schema 版本化，按页面允许的日期和后端实际来源 / 策略值校验；保存配置与页面选项复用定义。人群 / 快照不应偷偷持久化为永久有效；当前禁用人群状态下保存是合理约束。

## F4 · P2 · 删除远程群组失败会被包装成本地删除成功

位置：frontend/src/analytics/cohortClient.js:84–90。

**触发 / 复现**：模拟 DELETE 响应 401，deleteCohort 仍正常返回 `{deleted:true,source:'local'}`。catch 没有区分远程 id、登录失效、无权限和本地群组。

远程群组并未删除，用户得到成功语义；重新获取远程列表又会出现该群组。list/get 同样对所有错误回退本地，可能隐藏登录或权限问题。

**修复**：远程实体失败必须抛错；只有明确的 cohort_local_* 实体才能执行本地删除。本地离线保存应有明显状态及同步机制，401 / 403 / 404 不应切换数据来源。

## F5 · P2 · 标签全局预算会阻断正常分群，限制按成员关系而非独立用户计算

位置：backend/src/analytics/userTags.js:3–8；backend/src/routes/remoteAnalytics.js:102–107。

**复现**：内存库建立21个活动，每个活动为同一批5000人；独立用户只有5000，成员关系105000条。userTags 直接返回422。

所有 segments 请求都先加载全部运营标签，即使用户没有选标签，或只分析一个很小的群组，也会被这个全局限制阻断。现有活动名单固定，页面没有清理活动的常规入口，运营积累后难以自行解除。

**修复**：标签目录用数据库聚合人数，避免取全量成员；成员解析只读取所选标签，详情标签只读取当前分析人群。标签成员、独立用户、作业结果分别预算并给出明确单位；考虑归档活动但保留历史标签能力。

## F6 · P2 · 活动表单声明支持空格分隔，但解析器拒绝

位置：backend/src/analytics/activityMonitor.js:3；frontend/src/pages/activityMonitor.js:13。

**复现**：parseIds('123 456') 返回 ids=[]、invalid=['123 456']。表单占位提示写「也支持逗号或空格分隔」。KOL 新名单另做空格预处理，更加暴露入口不一致。

**修复**：活动、KOL、群组共用名单解析器，统一空白 / 逗号 / 换行 / 单列CSV及文件头处理。明确无效账号、格式错误和未匹配账号各自含义。

## F7 · P2 · 远程入口缺少未来时间过滤，可让数据截至时间跑到未来

位置：backend/src/data/hologres.js:56–64、85–102；backend/src/routes/remoteAnalytics.js:31–54。

**受控复现**：模拟 PG 返回一条已到达但 client_ts 在一年后的事件，status 返回未来365天的 as_of。ranked 只限制 server_ts 和 client_ts 非空，没有先校验 client_ts 范围；identity 和 facts 也建立在这些输入上。

**实际覆盖**：本次远程只读检查，已观测 future_events=0、negative_events=0。没有证据说明现在的生产北极星已被未来事件污染。

**修复**：在建立身份、首次事实及所有指标之前统一校验时间。as_of、latest_event_at、数据水位与查询截止分开，不让异常客户端时间决定未来统计期；排除原因应可核对。

## F8 · P2 · CRM 推荐贡献丢失微秒绑定顺序

位置：backend/src/data/kolMetrics.js:20–22；backend/src/analytics/kolMetrics.js:8–13。

推荐关系查询保留了 invitation_order 微秒值，现有推荐计算也使用它；CRM children 只带 Date.parse 后的毫秒 bound_at，贡献聚合用 t>=bound_at。

**复现**：绑定发生于1000900微秒，分析事件发生于1000000微秒，事件实际早于绑定；CRM 毫秒聚合仍计入1次。交易时间也经 Date.parse，存在相同边界问题。

**修复**：保留绑定原始精度；对毫秒事件用明确的微秒比较，不猜测同毫秒内顺序。交易在数据库时间精度下做绑定后条件。增加同毫秒内先后顺序回归用例。

## 功能设计评估

### 保留的方向

- 四个一级入口比原来十多个标签清晰，活动和 CRM 共用工作台合理。
- 活动 / KOL 稳定 ID 作为标签身份，名称只用于显示，避免改名丢成员。
- 标签交集 / 并集与每组内去重合理；重叠标签组人数不相加，已有说明正确。
- 固定活动名单、固定分析人群和同作业下钻能保证对账；CRM / 活动 / 新标签接口已做 owner 隔离。
- 缺数据保留未知，分析事件次数没有冒充精确操作次数，交易金额注明已知及部分覆盖，这些边界应保留。

### D1 · 标签过滤与固定人群混用，切换标签会累计取交集

frontend/src/pages/tagAudience.js 将当前 audience_ids 再传给新标签解析。先选不重叠的活动A，再改选活动B，得到A∩B，而不是B；标题仅列B，不保留此前A的条件。当前文案说明已有分析人群取交集，所以这是现有设计行为，但不符合普通「换筛选条件」的习惯。

建议区分「基础分析人群」与「当前标签过滤」，更换标签默认替换过滤；另给明确「与当前人群取交集」动作，并显示完整条件来源。

### D2 · 活动监控的历史名单与日常标签维护需要分开

固定活动名单有利于激活率对账，但日常运营往往需要补录 / 移出标签用户。目前活动标签直接来自冻结成员，无法给同一个活动持续追加标签用户而不改变统计分母。

建议保留活动参与名单版本 / 冻结基线，再提供独立可维护的当前标签成员；新增参与者作为新批次，不重写已结算结果。若产品明确只支持一次性活动，需在入口说明此限制。

### D3 · KOL 详情的三种人群范围尚未统一呈现

CRM 当前展示本人和正式一级邀请贡献；新加的 KOL 标签名单不进入 CRM 指标聚合。只录入标签名单而未关联本人账号时，CRM 卡片仍全部待关联，用户容易以为名单没有生效。

建议明确三块：KOL 本人、直接邀请用户、手动标签用户。手动名单支持「查看这批用户的使用 / 交易表现」，避免让手动标签等价于正式归因。

### D4 · 快照15分钟寿命缺少直接恢复动作

标签应用后锁定 snapshot_id，顶部刷新更新可用数据，但仍沿用旧人群快照；过期会报409。当前通常要清除人群再重选标签。建议显示名单固定时间与数据截至时间，并提供「保留名单，使用新数据重新分析」的显式动作，不能无提示更新分母。

### D5 · 运营标签、KOL档案标签、标签群组三种概念命名重复

KOL 自由文本 tags 是档案分类；活动 / KOL 用户标签是业务成员关系；左侧「标签群组」是另一个保存名单功能。建议改名为「KOL分类」「运营标签」「固定用户群」，并提供一个统一的人群入口，减少重复筛选器和状态来源。

## 已知数据能力缺口，不能算本轮新发现的代码缺陷

精准分析操作次数仍依赖产品完成事件、稳定操作ID、结果状态与曝光区分；目前观察事件次数是兼容口径。完整采集、水位、历史首次、链上最终结算、费用 / ROI 等也尚未具备完整证据。补采集与业务事实契约比新增图表更优先。

## 修复次序

1. F1：群组账号归属与权限贯穿读写、分析和迁移。
2. F2：统一交易身份事实，核对历史用户池 / 推荐 / CRM差异。
3. F3、F4、F6：修复用户直接遇到的保存、删除和导入问题。
4. F5：按目标人群查询标签，解除对普通分群的全局阻断。
5. F7、F8：补异常输入与精度边界回归。
6. D1–D5：统一人群操作模型与命名，再扩展运营功能。

审计阶段没有创建或修改正式业务记录，没有写远程业务库。
