## 可重复执行

```sh
cd backend
npm run audit:tracking -- --days 7
```

输出为聚合JSON。支持1–31天；遇到上下文超过5000条或8MiB直接失败，不截断后宣称完整。脚本会为当前窗口相关用户读取更早诊断起点，避免把跨窗终态误判为没有起点。行为窗口按client_ts，采集对账按server_ts，两者分别输出。

脚本不启动HTTP服务、不跑数据库迁移、不输出用户ID、event_id、原始属性或凭据。数据库账户仍应由环境配置只读权限。对账读取不是数据库事务快照，源表修改期间可能不一致，应重新获取快照重查。

## 产品端需要核对/补齐的具体能力

### 登录尝试：当前优先

页面已有，不需要再做一套Dashboard。

- `login_attempt_started`：唯一login_attempt_id、login_method；按真实主动尝试发起，不把自动恢复计入主动尝试。
- `login_attempt_finished`：同一login_attempt_id，outcome=success/failed/cancelled，非负duration_ms；明确失败提供error_stage/error_code，明确取消提供cancel_reason。
- `login_stage_started/finished`：同一父login_attempt_id，每次阶段尝试独立stage_attempt_id及stage；终态提供outcome和duration_ms；重试不能覆盖前一次尝试。
- 保留现有login_succeeded，继续区分manual/auto_restore。不能仅有成功事实就倒推出登录尝试成功率。
- 先核对线上版本、事件触发条件、发送队列和collect落库；数据库没记录不等于产品源码完全没有实现。

### 免费试用：需要明确业务事实

当前myMonitor直接识别已登录账号的`free_trial_started`。仅在试用权益真实开启后记录；浏览页面、点击入口和人工赠送不能直接等同试用开启。若权威事实已在业务表，应优先核对该表再决定是否补事件。当前只确认缺事件，未替产品设计新的试用权益规则。

### 分析请求：扩大覆盖，不重写既有口径

analysis_requested/finished及analysis_request_id已有。下一步验证主动操作、首次加载、后台刷新、缓存命中、空结果、失败、取消和重试的实际样本；发送重试保持同event_id，业务重新请求使用新request_id及明确retry_of_request_id。保留北极星的筹码查看/下钻观测口径，不能凭13次样本直接替换历史分析次数。

### 邀请：显式流程为增强，不阻塞已完成的注册校验

现有注册邀请校验复用referral、身份、账号及邀请关系。它不要求额外flow ID。只有进一步做逐阶段验证/绑定失败诊断时，才继续接invite_validation_finished、invite_binding_finished和现有显式流程契约；不能为填满页面虚构绑定事实。

### 页面加载：处理7次未知的证据

按既有埋点验收页查其实际event_id，核对导航取消、旧版本仅上报started、页面关闭/网络失败或确实未结束。没有终态证据不能改成失败或成功。ready/presented继续按页面业务定义选择，不把骨架屏视为数据就绪。

## 一条真实链路的验收条件

1. 在产品浏览器执行一次真实动作，保留安全事件样本（event_id、事件名、client_ts和契约白名单属性）。
2. 保留对应collect的HTTP状态与业务响应；HTTP 200本身不是业务成功证明。
3. 使用已有埋点验收页，以相同event_id查询新快照；核对原始到达、事实纳入、字段契约和样本一致性。
4. 在相同统计窗口和人群下核对对应报表与名单；数据库有记录不等于一定进入每个指标。
5. 覆盖成功、失败、取消、自动恢复、重试、跨页/切Token等真实分支；缺失分支保持未验收状态。
